# Chapter 27: The Clean Architecture

## Architecture

Over the last several decades, software development has produced many architectural ideas, including:

- Hexagonal architecture, also called Ports and Adapters.
- Data, Context, and Interaction (DCI) architecture.
- Boundary–Control–Entity (BCE) architecture.

Though these architectures vary in detail, they have the same objective: separation of concerns. They achieve this by dividing software into layers. Each has at least one layer for business rules and another for user and system interfaces.

These architectures produce systems that are:

- Independent of frameworks. The architecture does not depend on a feature-laden library, so frameworks can be used as tools rather than dictating the shape of the system.
- Testable. Business rules can be tested without the UI, database, Web server, or other external element.
- Independent of the UI. A Web UI can be replaced by a console UI without changing the business rules.
- Independent of the database. A database can be replaced with another database technology without binding the business rules to it.
- Independent of external agencies. Business rules do not know anything about interfaces to the outside world.

## The Dependency Rule

The concentric circles in Clean Architecture represent different areas of software. In general, the farther inward you go, the higher-level the software becomes. The outer circles are mechanisms; the inner circles are policies.

The overriding rule is the Dependency Rule:

> Source-code dependencies must point inward, toward higher-level policies.

Nothing in an inner circle can know anything about something in an outer circle. In particular, code in an inner circle must not mention the names of functions, classes, variables, or other software entities declared in an outer circle.

Data formats declared in an outer circle should not be used by an inner circle, especially when those formats are generated by a framework. Nothing in an outer circle should affect the inner circles.

## Entities

Entities encapsulate enterprise-wide critical business rules. An entity can be an object with methods or a set of data structures and functions. What matters is that entities can be used by many applications in the enterprise.

If there is no enterprise and the system is a single application, the entities are the application’s business objects. They encapsulate the most general and highest-level rules and are least likely to change when external elements change. A change to page navigation or security, for example, should not affect the entity layer.

## Use Cases

The use-case layer contains application-specific business rules. It encapsulates and implements all the use cases of the system. Use cases orchestrate the flow of data to and from entities and direct those entities to apply their critical business rules.

Changes in this layer should not affect the entities. This layer should also be isolated from external concerns such as the database, UI, and common frameworks. Changes to how the application operates may affect the use cases, so changes to a use case will affect code in this layer.

## Interface Adapters

This layer contains adapters that convert data from the format most convenient for use cases and entities to the format most convenient for an external agency such as a database or Web interface.

The presenters, views, and controllers of an MVC architecture belong here. Models are usually data structures passed from controllers to use cases and then back to presenters and views. Data is also converted here from the form convenient for entities and use cases into the form convenient for persistence.

No code inward of this circle should know anything about the database. If the database is relational, SQL should be restricted to this layer, particularly to its database-related parts. Other adapters convert external service data into the internal form used by use cases and entities.

## Frameworks and Drivers

The outermost layer is composed of frameworks and tools such as the database and Web framework. Generally, little code is written here beyond glue code that communicates with the next circle inward. This is where the details go. The Web is a detail, and the database is a detail; they remain on the outside where they can do little harm.

## Only Four Circles?

The circles are schematic. You may need more or fewer layers. There is no rule that requires exactly four circles. The Dependency Rule always applies.

As you move inward, the level of abstraction and policy increases. The outermost circle contains low-level concrete details. The innermost circle contains the most general and highest-level policies.

## Crossing Boundaries

Controllers and presenters communicate with use cases in the next layer. The flow of control begins in the controller, moves through the use case, and eventually executes in the presenter. The source-code dependencies, however, point inward toward the use cases.

This apparent contradiction is resolved with the Dependency Inversion Principle. In a language such as Java, interfaces and implementation relationships are arranged so that source-code dependencies oppose the flow of control at the appropriate points.

For example, a use case may need to call a presenter. The call cannot be direct because that would violate the Dependency Rule: an inner circle cannot mention a name in an outer circle. Instead, the use case calls an interface such as `UseCaseOutputPort` in the inner circle, and the presenter in the outer circle implements it. Dynamic polymorphism allows the source-code dependencies to point inward regardless of the direction of control flow.

## What Data Crosses the Boundaries?

Data crossing boundaries should normally be represented by simple data structures. These may be basic structs, simple data-transfer objects, function arguments, maps, or plain objects.

The important point is that the structures are isolated and simple. Do not pass entities or database rows across a boundary. A database framework may return a convenient row structure, but passing that row inward would force an inner circle to know about an outer circle.

Data should cross a boundary in the form most convenient for the inner circle.

## A Typical Scenario

Consider a Web-based system using a database. The Web server gathers input from a user and passes it to a controller. The controller packages the input into a plain object and passes it through an input boundary to a use-case interactor.

The interactor interprets the data, controls the entities, and uses a data-access interface to load entity data from the database. When the use case completes, the interactor gathers data from the entities and constructs output data as another plain object. It passes this object through an output-boundary interface to a presenter.

The presenter repackages the output data into a view model. The view model contains strings and flags that the view can display directly. Dates, currencies, button names, menu names, and display-state flags are formatted or selected by the presenter rather than by the view.

The view then has little to do beyond moving the view-model data into the HTML page. All dependencies cross the boundary lines inward, following the Dependency Rule.

## Conclusion

Separating software into layers and following the Dependency Rule creates a system that is intrinsically testable. When an external part becomes obsolete, such as a database or Web framework, it can be replaced with minimal disruption.
